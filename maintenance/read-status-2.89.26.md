# Read status and recent successful data — 2.89.26

All mapped data views now expose the existing Satori “Stav údajov” disclosure. It covers fulfillment, ranking, team fulfillment, calendar, board, stocks, pharmacies and packaging, visits/history, surveys, activity, reports, market data, district charts and navigator sources. Section rows identify their own successful check, pending read or failure; product/quarter batches are separate. Unknown data remain neutral. Success is green with a check mark, failure red with text, and pending work uses the existing spinner. A previous successful time is labelled as such while a refresh is pending or failed. Expanded details and spinner nodes survive status repainting; cached page content remains visible.

Successful read responses can be reused within the same account, role, line and login epoch. Collaborative board/calendar responses have a 30-second window; other reads have a five-minute window. A cache hit retains the actual server verification time. First login, expired responses, different filters/periods/colleagues, invalid responses and explicit pull/retry use the normal loaders. Unknown query parameters disable response reuse. Graph/previous-quarter completeness flags and bootstrap parts are included in request identity. Stored response JSON isolates callers' mutations and has bounded memory (48 entries, three million characters total, 600,000 characters per response); oversized responses fall through to the existing loading path.

Home checks each section independently, so expiry of board/calendar data does not re-download current sales, ranking or stocks. Completed successes remain recorded when the user leaves the screen; stale epochs and superseded replies cannot replace a later check. Writes invalidate reusable responses and a version guard prevents an earlier in-flight reply restoring them. Foreground board/calendar notifications invalidate their corresponding data before refresh. Explicit stock, activity, report-market and navigator controls bypass reuse; pharmacy retry includes packaging and saved filters. Report retry also includes agreements. The status UI observes existing requests rather than introducing another automatic fetching loop.

A fast-return regression exposed an old panel animation hiding a reopened Home. Animation cleanup now respects the current panel and the most recent animation of each node. No backend endpoint, permission rule, authentication scope, ranking/team period behavior or form submission semantics changed. Apps Script redeployment is not required.

Validation includes 33 source suites, a 552-case section/role/line matrix in each source, a 24-session response-reuse matrix in each source, and a 489-case mobile browser matrix using actual view mapping. Real Home loaders are tested across 21 role/line combinations for first verification, short returns with zero repeated reads, selective expiry, partial failure, explicit retry and resume deduplication. Additional browser regressions cover 126 failure/recovery cases and a 14-second server reply, navigator entity loading and routes, report market refresh, pharmacy September history, district scopes, manager login/line switching, planned-quarter selection, request performance, trusted Android/iPhone pull gestures and spinner stability. Live/preview source equality and built asset hashes/service-worker references are checked.

Browser tests use synthetic accounts and deterministic backend responses. They do not establish physical-device behavior, real Google service latency or end-to-end production notification delivery. No authenticated live data are edited by these tests.

Run `npm test` and `npm run build`. For browser tests set `SATORI_TEST_BUILD=1` and `SATORI_PLAYWRIGHT` to the installed Playwright module. The new focused suites are `test-read-status-browser.cjs`, `test-read-session-cache.cjs`, `test-read-sections.cjs`, `test-panel-fast-return.cjs` and the extended `test-home-resume-browser.cjs`.
